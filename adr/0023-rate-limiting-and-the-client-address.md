# ADR-0023 — Rate limiting: Bucket4j on Redis, failing open; the trusted-proxy client address; keyed hashes for personal identifiers

**Status:** Accepted · **Date:** 2026-09-24 · **Amended:** 2026-11-08 (two buckets for typed codes, #135); 2026-11-09 (`auth:code:email` fails closed, owner's ruling)

## Context

FR-012 fixes the numbers: five sign-in attempts per fifteen minutes per account, twenty an hour per IP, three registrations an hour per IP, three password-reset requests an hour per email, `429` with `Retry-After`. Doc 06 §4 adds the global authenticated bucket and the header triple `X-RateLimit-Limit / Remaining / Reset`. Doc 25 D6 fixes the store — Bucket4j on Redis, "the one with a real argument: every unauthenticated request writes", and a login brute-force must not write to the database the product depends on — and doc 07 §5 fixes the key shape (`rl:{bucket}:{key}`) and the rule that Redis is "a cache and coordinator, never a source of truth". T-18 fixes the shape of the login limit: per-IP *as well as* per-email, "regardless of whether the address exists", because a limit only real accounts can hit tells an attacker which accounts are real. Doc 07 §2 has carried `consent_records.ip_hash` and `user_agent_hash` as nullable since slice B, with a comment saying they wait for "the trusted-proxy resolver", which this slice is.

What none of those documents say: how the limiter behaves when Redis is not there; which address counts as the client behind kamal-proxy and Cloudflare (ADR-0011); how an address becomes a hash; what the headers say when two buckets apply; and what a person who hit a limit is told. Slice F decides those.

The course's answer, for contrast: Chirp hand-writes a Lua token bucket over `StringRedisTemplate`, resolves the client from `X-Real-IP` against one trusted proxy, and ends a limited request with `response.sendError(429)` — which drops the `Retry-After` FR-012 requires.

## Decision

**1. Bucket4j over the Lettuce connection Spring Boot already configures.** `spring-boot-starter-data-redis` owns the connection (`spring.data.redis.*` in production, `@ServiceConnection` in tests); Bucket4j's Lettuce adapter owns the bucket arithmetic — refill, compare-and-swap between concurrent consumers, the Lua that makes one consume atomic. The adapter is built against Lettuce 6 and declares it `provided`; Boot 4.1 ships Lettuce 7, and the three calls it makes (`EVAL`, `GET`, `DEL`) are the same in both — proven by the limiter's integration tests against a real Valkey 8, not by the compile. In D5's terms: the library writes the arithmetic, we write the key, the clock and the failure policy, and no bucket maths is written here. Bucket4j reads time through the injected `Clock`, which is what lets a test refill a fifteen-minute bucket without waiting fifteen minutes.

**2. The buckets are code, not configuration.** `RateLimitBucket` is doc 06 §4's table as an enum — name, subject, capacity, period. A limit that can be loosened in an environment file is not the limit the threat model was written against. Three shapes are added to the table, recorded here and in `06`: **`auth:resend` per email, one a minute**, the cooldown `states.md` §1 promised the "send again" button and the table omitted; and **a per-IP bucket of twenty an hour on `forgot-password` and `resend-verification`**, because both send email to whoever asks and a per-address limit alone bounds nothing an attacker cannot vary. Refill is **greedy**: five per fifteen minutes returns one token every three minutes rather than five on the quarter hour. The rate is identical; the wait the person is told is shorter and honest.

**3. Where each bucket is consumed.** A per-IP bucket is consumed by one `HandlerInterceptor`, before the handler and before the body is read, on any method annotated `@RateLimited(bucket)`; a malformed request spends a token too, which is the stricter reading and the only one an interceptor can give. The per-user bucket is consumed by the same interceptor on every request carrying a verified bearer token, with no annotation. A per-email bucket is consumed **in the service** — `LoginUser`, `RequestPasswordReset`, `ResendVerification` — because the address is in the body, keyed on the lowercased address as typed and counted for every address alike, so the 429 says nothing about whether an account exists. In `LoginUser` it is the first thing that happens: a refused attempt costs no Argon2id.

**4. The response.** `429`, `code: RATE_LIMITED`, RFC 9457 like every other error, `Retry-After` in whole seconds rounded up, and the header triple with zero remaining; the detail is `states.md` §1b's copy — *"Please wait 3 minutes before trying again."* — the wait and nothing else, not the bucket, not the count, not the word "attempts". On a **successful** response the headers describe the bucket the interceptor consumed with the fewest tokens left; a 401 from the service still carries them. On a 429 raised by a service bucket, the headers describe that bucket. `X-RateLimit-Reset` is Unix seconds (GitHub's convention) at which the bucket is full again, which after a single consume is one refill interval away, not the whole period. The interceptor throws rather than writing the response, so the 429 goes through the same `@RestControllerAdvice` chain as everything else and the headers are set once, in `SecurityExceptionHandler`.

**5. Fail-open, loudly.** If Redis does not answer, the answer is *allow*, and the request proceeds without headers. Doc 07 §5's rule decides it: Redis is a coordinator, never a source of truth, and a cache outage must not become an authentication outage. What still stands when the limiter is gone: Argon2id's per-attempt cost, the silent exponential lockout in Postgres (ADR-0020), and the unique constraints. "Loudly" is three things: a WARN at most once per five seconds rather than once per request; the counter `moyi.rate_limit.backend_unavailable`, which is what an alert watches; and a five-second hold after a failure during which Redis is not tried at all, so an outage costs one timeout per interval rather than one per login. When the hold expires, a compare-and-set gate lets **one** caller probe while every other request keeps failing open, and only the caller that moves the hold forward writes the WARN — without that gate every request that saw the expired hold probed together, which Codex's review of #33 caught: N timeouts per interval under load, not one. The same gate covers first contact: the limiter starts as if a hold had just expired, because the lazy connection is a synchronised initialiser and a burst of first callers against a dead Redis would otherwise queue on it, each paying the connect timeout in turn (a second review of #33 caught this; the test drives twenty concurrent first calls at a non-routable address and bounds the total wait to one timeout). The timeouts are short on purpose — 500 ms to connect, 250 ms per command — because Lettuce's default is sixty seconds, which is a login outage by another route. **The Redis health indicator is disabled**: kamal-proxy routes on `/actuator/health`, and reporting DOWN for a cache would take the application out of rotation to protect the thing it can live without. The application boots with Redis absent; the first consume connects. *(Amended 2026-10-30, ADR-0053 decision 13: the connection is checked before each use and made again when it is closed or the connection factory's client has changed, after a factory stop and start left the limiter failing open for good.)* `moyi.security.rate-limit.enabled=false` replaces the limiter with one that allows everything and says so at WARN on every start — a test context's lever and an operator's, not a deployment option. *(Amended 2026-11-09: one bucket, `auth:code:email`, fails closed instead; see the amendment of that date.)*

**6. The client address: walk `X-Forwarded-For` from the right, past the proxies we trust.** `moyi.security.client-address.trusted-proxies` is a list of CIDR ranges. The socket address, if trusted, is skipped; then the header's entries from right to left, skipping each trusted one; the first untrusted entry is the client. Anything to its left was written by somebody we do not trust and is ignored, which is what makes a forged header worthless. **An empty list means no header is believed** and the socket is the client — over-strict behind a proxy (every request shares one address, and the per-IP limits say so at once) rather than spoofable, and correct on a laptop. Header entries are parsed as literals and never resolved: `InetAddress.getByName` on an attacker's string is a DNS lookup on the request thread, and an unbracketed string that fails the JDK's IPv6 literal parse is handed to the name service as a hostname — so IPv6 candidates are bracketed before parsing, which makes the contract literal-or-throw. An entry that does not parse ends the walk. **IPv6 is keyed on its /64**: an ordinary allocation is at least that, and a per-/128 bucket hands one connection 2^64 fresh keys. `consent_records` stores the hash of the full address; the key truncation is the limiter's alone. The `local` profile trusts loopback so that a request from the developer's own machine may name its client with the header, which is how `scripts/smoke.sh` gives each probe an address and drives every per-IP bucket to its 429 against the real jar.

**7. Personal identifiers are hashed with a keyed hash and a configured secret.** `PersonalDataHasher` is HMAC-SHA256 over `moyi.security.hashing.secret`, base64url, forty-three characters. Plain SHA-256 of an IPv4 address is reversible by hashing all 2^32 of them, which takes minutes; the secret is the only thing that turns "we store hashes" from a courtesy into a control. The same hasher keys every Redis bucket, so no address or email is a Redis key in the clear (NFR-044). The secret **fails closed** like the signing key (ADR-0019): `secret-source` defaults to `CONFIGURED`, which refuses to start without at least thirty-two characters from the environment; `EPHEMERAL` is set only by the `local` profile and test contexts, and logs at WARN. Registration now fills `ip_hash` and `user_agent_hash`, which closes the note doc 07 §2 has carried since slice B; V3's own column comment still says "NOT populated yet" because a Flyway migration is immutable once applied, and this ADR is where the correction lives.

**8. The rate limit and the lockout are two layers, and the rate limit fires first.** With five per fifteen minutes per email and a lock after five failures (ADR-0020), the sixth attempt inside the window is a 429 and the lock is never observed over HTTP until a token refills. That is the intended order: the bucket is the cheap front door — no Argon2id, no database write — and the lockout is the durable one that survives a Redis outage and counts across addresses. The endpoint tests turn the limiter off for the shared context, because the lockout tests sign in six times in a row, and one dedicated context turns it on and proves every bucket; the smoke script flushes the compose Valkey between sections for the same reason.

## Consequences

**Positive.** Every bucket in doc 06 §4 that has an endpoint is enforced, each 429 carries `Retry-After`, and the headers are on every limited response (doc 12 §3.3). A login brute-force writes to Redis and never to Postgres. A Redis outage costs limits, not logins, and is visible on a counter. A forged `X-Forwarded-For` buys nothing; a misconfigured proxy list under-trusts rather than over-trusts. The consent rows carry evidence that cannot be turned back into an address. No bucket maths, no Lua and no address parsing beyond a shape check is hand-written.

**Negative.** A 422 spends a per-IP token. A person who signs in on six devices inside fifteen minutes waits three minutes. Two more required environment values before anything but `local` boots (`MOYI_SECURITY_HASHING_SECRET`, and the proxy ranges in production). `common:security` now carries Spring Data Redis and Bucket4j, and so does `tools:breach-corpus`, which depends on it for the Bloom filter and calls none of this; ADR-0019 already named that smell. The `local` profile trusting loopback means a process on the same machine can claim any address — acceptable for a laptop and wrong anywhere else, which is why it is profile-scoped. Bucket4j's Lettuce adapter is one major version behind the Lettuce we run; the integration tests are the guard, and a Lettuce 8 that changes `eval` would fail them, not production.

**Neutral.** The `X-RateLimit-*` names are doc 06's; the IETF draft (`RateLimit`, `RateLimit-Policy`) may be adopted later as an addition. The kill switch exists and is documented as not a deployment option; the WARN on every start is what keeps it honest. Doc 07 §5's fifteen-minute cache of `tokens_invalid_before` is still not built; the Redis slice this ADR belongs to could carry it, and it must sit behind the `TokenRevocations` port with Postgres as the fallback (ADR-0019), which is a separate change.

## Alternatives considered

- **Chirp's hand-written Lua bucket over `StringRedisTemplate`.** Rejected by D6 (Bucket4j is named) and by D5's spirit: the compare-and-swap and refill arithmetic are exactly the code that is wrong in a subtle way first. Good to read for atomicity; not to ship.
- **Bucket4j's JDBC backend on Postgres.** Rejected for now by D6's own argument — every unauthenticated request writes — and kept as the fallback D6 names if Redis is cut for memory: a one-session change behind the `RateLimiter` port.
- **Fail closed.** Rejected: it converts a cache outage into an authentication outage, and the controls that remain are adequate. Revisit if a credential-stuffing run is ever observed coinciding with a Redis outage.
- **Tomcat's `RemoteIpValve`** (`server.forward-headers-strategy=native`). It does this job, rewrites `remoteAddr` for everyone, and is the answer in a Tomcat-only shop. Rejected because its trusted list is a regular expression, which for Cloudflare's published ranges is unreadable, and because a class the tests can hold with a CIDR list is smaller than the valve's configuration. Spring's `ForwardedHeaderFilter` trusts every hop and was never a candidate.
- **`CF-Connecting-IP`.** Cloudflare's own header names the client directly; trusting it means trusting that only Cloudflare can reach the origin. Not built; the CIDR list can express "trust Cloudflare's ranges" when the deployment is real, and the header can be added then if the walk proves fragile.
- **Plain SHA-256 for `ip_hash`.** Rejected; see decision 7. A pepper in code rather than configuration was rejected for the same reason a signing key in the repository was.
- **Refund the login token on success.** Considered so that a person signing in repeatedly is never limited; rejected as one more branch on the success path for a case (six sign-ins in fifteen minutes) that a single account does not have.
- **Per-/128 IPv6 keys.** Rejected; see decision 6.

## Revisit when

Redis is cut during Phase 5 load testing (move to Bucket4j's JDBC backend behind the same port). A second application node exists (the buckets are already shared; the hold and WARN are per process). The deployment is real and Cloudflare's ranges have to be configured (and refreshed — they change). The invite buckets of doc 06 §4 arrive with Phase 2 (`invite:lookup` + `invite:accept` share one per-IP bucket, which needs a bucket that two annotations can name). A 429 is ever seen on a legitimate client's ordinary use of `/me` polling (raise the global bucket, or shape the client). Lettuce 8.

## Amendment — 2026-11-08: the typed-code buckets, and the guess budget they leave (#135)

`verify-email` and `reset-password` had no bucket of their own: they took a 256-bit token, which no rate of guessing reaches. A six-digit code is one of 10^6, so both routes now carry two buckets, as code (decision 2).

**1. `auth:code:ip`, twenty an hour per client address, on both routes together**, consumed by the interceptor before the body is read (decision 3), for links and codes alike, the way the invite routes share `invite:code:ip`. It bounds one address spraying codes across many accounts: at most 480 tries a day, spread over whichever addresses it names.

**2. `auth:code:email`, ten a day per address as typed, on both routes together**, consumed in the service (`VerificationCodeCheck.limit`) and only for the code form, before any lookup, for every address alike, so the 429 is no oracle. Greedy refill: one try back every 2.4 hours, which is the `Retry-After: 8640` a person meets.

**3. The arithmetic.** A code is burned after five wrong tries (ADR-0018, amended): one code gives a guesser at most 5 / 10^6 = 1 in 200,000. Codes can be asked for again (`resend-verification` once a minute, `forgot-password` three an hour per address), so the per-code limit alone bounds nothing over a day; the per-address bucket does: **at most ten tries a day against one account, whatever is re-requested and from however many addresses**, so at most 10 / 10^6 = **1 in 100,000 a day**, or about 1 in 274 over a year of continuous attack. Using even those ten needs at least two codes a day, and every code is an email to the owner of the address, so a sustained attempt is visible to its target. For reset (an account takeover) that is the number that matters; for verification the prize is a verified address its holder does not own.

**4. Fail-open still applies, and costs more here.** With Redis down (decision 5) neither bucket is consumed, nor is the issuing cooldown, so the budget per day becomes five per code times as many codes as can be asked for. What still stands: the burn at five, the fifteen minutes, one code per account at a time, and every code an email to the owner. **Whether these two routes should fail closed is an owner question**, recorded rather than decided: failing closed would turn a Redis outage into "you cannot verify or reset by code" while the link still works. *(Decided 2026-11-09, below: the typed code fails closed; the link, and every other bucket, fail open.)*

`RateLimitingEndpointTest` drives both to their 429 (`ten typed codes a day per address…`, `twenty presentations an hour from one client address…`), and `scripts/smoke.sh` does too, against the compose Valkey; removing either the annotation or the service's consume turns its test red.

## Amendment — 2026-11-09: a typed code fails closed (owner's ruling)

The security review of #155 put a number on the paragraph above: with Redis down, `auth:code:email`'s ten a day is gone, and the only bound left on guessing one account's code is five wrong tries per code, which a re-request resets (and the issuing cooldowns are Redis buckets too). The owner ruled on 2026-11-09: **when Redis cannot be reached, refuse typed codes until it is back; links keep working.** Decision 5 is unchanged for everything else.

**1. One bucket fails closed: `auth:code:email`.** `RateLimitBucket` gains `failsClosed` (default `false`), set on that bucket alone, so the policy is in the closed table where the buckets are reviewed. `RateLimitFailurePolicyTest` pins the set to exactly that one bucket: a second bucket that refused requests while Redis is down would be the login outage decision 5 exists to prevent, and adding one is now a visible change to a test beside an ADR.

**2. The limiter still never throws; the consumer refuses.** `RedisRateLimiter` answers `Unavailable` for every bucket as before (the hold, the probe gate, the WARN and the counter unchanged). `VerificationCodeCheck.limit`, the bucket's only consumer, turns `Unavailable` into `CodeCheckUnavailableException` when the bucket fails closed. It runs before any read, as the 429 does, so the code is not looked up, compared, counted or spent, and the answer is the same bytes (but the `traceId`) for an address with an account and one without. Only the `{email, code}` form reaches it; `{token}` never consumes this bucket.

**3. The answer: `503 CODE_CHECK_UNAVAILABLE` with `Retry-After: 60`.** 503 rather than 429, because the caller did nothing too often: the server cannot do its part. A code of its own, not `RATE_LIMITED` (whose `Retry-After` is a true wait for a token, and whose client copy is "please wait") and not `HASHING_CAPACITY_EXCEEDED` (which clears in milliseconds and asks for the same request again). The detail names the way that works now: "Use the link in the same email, or try the code again in a minute." Sixty seconds is the detail's minute; the limiter re-probes Redis every five seconds, so the server notices recovery long before a person retries. A new enum value in the problem's `code`, so the contract change is breaking for a generated client (oasdiff `response-property-enum-value-added`) and the PR carries `breaking-api-change`.

**4. A switched-off limiter is not an outage.** `enabled=false` used to answer `Unavailable` too. It now answers a decision of its own, `Disabled`, which lets the code through: the module test contexts run with the limiter off, and an operator who switches it off has chosen no limits, not a Redis outage. `EmailCodeEndpointTest` runs with the limiter off and fails twelve of thirteen if `Disabled` is folded back into `Unavailable`.

**5. What stays open.** `auth:code:ip` (twenty an hour per client address, both routes, links and codes) still fails open: it is consumed by the interceptor for the link too, and closing it would refuse the link, which the ruling keeps working. That costs nothing here: while Redis is down every typed code is refused at `auth:code:email` anyway, so the open per-address bucket lets through only links, which nobody can guess. The issuing cooldowns (`auth:resend:email`, `auth:reset:email` and their per-IP buckets) also fail open: they bound email sent, not guesses, and while codes are refused a new code cannot be typed anyway. `auth:login:*` fails open as before (decision 5).

**Tests.** `TypedCodeRedisOutageTest` (identity), limiter on, Redis a port nothing listens on, as `RedisOutageTest` does it (no container to stop, so none of the Testcontainers restart trouble): a typed verification code is 503 with `Retry-After: 60`, `code_attempts` 0 and the row unspent; the same bytes for an unknown address; the link beside it verifies and sign-in is served (`auth:login:*` failing open); a typed reset code is 503 and spends nothing, the reset link then works. With the throw removed, all four go red. `scripts/smoke.sh` gains no outage probe: its default run drives the compose Valkey that every checkout and worktree shares (`flush_buckets` already reaches into it), so stopping it mid-run would take the limits away from whatever else is running against it, and every rate-limit probe after it would depend on the restart. The outage is proved by the test; the smoke run proves the typed codes still work with Valkey up, as before.

**6. Two edges, accepted.** *A healthy Redis can still refuse a typed code for one round trip.* The probe gate of decision 5 also covers first contact and the end of every hold: one caller asks Redis while every concurrent caller is answered `Unavailable`. Before this amendment those callers went through unlimited; a typed code among them is now a 503 although nothing is wrong. The window is one Redis round trip (at most the 250 ms request timeout) after boot and after each outage, the person has the link, and the retry the detail asks for succeeds. Removing the gate for this bucket would bring back the queue of first callers decision 5 was amended to prevent. *`enabled=false` lifts the ten-a-day bound*: decision 4 above makes the switched-off limiter allow, so the operator's lever is also the one state in which typed codes are unbounded; `RateLimitProperties.enabled` says so.

**Revisit when** the limiter moves to a JDBC backend (above: then `auth:code:email` could be counted in Postgres and never be unavailable while the database is up), or the 503 is ever seen in production for longer than a Redis restart.
