# ADR-0023 — Rate limiting: Bucket4j on Redis, failing open; the trusted-proxy client address; keyed hashes for personal identifiers

**Status:** Accepted · **Date:** 2026-09-24

## Context

FR-012 fixes the numbers: five sign-in attempts per fifteen minutes per account, twenty an hour per IP, three registrations an hour per IP, three password-reset requests an hour per email, `429` with `Retry-After`. Doc 06 §4 adds the global authenticated bucket and the header triple `X-RateLimit-Limit / Remaining / Reset`. Doc 25 D6 fixes the store — Bucket4j on Redis, "the one with a real argument: every unauthenticated request writes", and a login brute-force must not write to the database the product depends on — and doc 07 §5 fixes the key shape (`rl:{bucket}:{key}`) and the rule that Redis is "a cache and coordinator, never a source of truth". T-18 fixes the shape of the login limit: per-IP *as well as* per-email, "regardless of whether the address exists", because a limit only real accounts can hit tells an attacker which accounts are real. Doc 07 §2 has carried `consent_records.ip_hash` and `user_agent_hash` as nullable since slice B, with a comment saying they wait for "the trusted-proxy resolver", which this slice is.

What none of those documents say: how the limiter behaves when Redis is not there; which address counts as the client behind kamal-proxy and Cloudflare (ADR-0011); how an address becomes a hash; what the headers say when two buckets apply; and what a person who hit a limit is told. Slice F decides those.

The course's answer, for contrast: Chirp hand-writes a Lua token bucket over `StringRedisTemplate`, resolves the client from `X-Real-IP` against one trusted proxy, and ends a limited request with `response.sendError(429)` — which drops the `Retry-After` FR-012 requires.

## Decision

**1. Bucket4j over the Lettuce connection Spring Boot already configures.** `spring-boot-starter-data-redis` owns the connection (`spring.data.redis.*` in production, `@ServiceConnection` in tests); Bucket4j's Lettuce adapter owns the bucket arithmetic — refill, compare-and-swap between concurrent consumers, the Lua that makes one consume atomic. The adapter is built against Lettuce 6 and declares it `provided`; Boot 4.1 ships Lettuce 7, and the three calls it makes (`EVAL`, `GET`, `DEL`) are the same in both — proven by the limiter's integration tests against a real Valkey 8, not by the compile. In D5's terms: the library writes the arithmetic, we write the key, the clock and the failure policy, and no bucket maths is written here. Bucket4j reads time through the injected `Clock`, which is what lets a test refill a fifteen-minute bucket without waiting fifteen minutes.

**2. The buckets are code, not configuration.** `RateLimitBucket` is doc 06 §4's table as an enum — name, subject, capacity, period. A limit that can be loosened in an environment file is not the limit the threat model was written against. Three shapes are added to the table, recorded here and in `06`: **`auth:resend` per email, one a minute**, the cooldown `states.md` §1 promised the "send again" button and the table omitted; and **a per-IP bucket of twenty an hour on `forgot-password` and `resend-verification`**, because both send email to whoever asks and a per-address limit alone bounds nothing an attacker cannot vary. Refill is **greedy**: five per fifteen minutes returns one token every three minutes rather than five on the quarter hour. The rate is identical; the wait the person is told is shorter and honest.

**3. Where each bucket is consumed.** A per-IP bucket is consumed by one `HandlerInterceptor`, before the handler and before the body is read, on any method annotated `@RateLimited(bucket)`; a malformed request spends a token too, which is the stricter reading and the only one an interceptor can give. The per-user bucket is consumed by the same interceptor on every request carrying a verified bearer token, with no annotation. A per-email bucket is consumed **in the service** — `LoginUser`, `RequestPasswordReset`, `ResendVerification` — because the address is in the body, keyed on the lowercased address as typed and counted for every address alike, so the 429 says nothing about whether an account exists. In `LoginUser` it is the first thing that happens: a refused attempt costs no Argon2id.

**4. The response.** `429`, `code: RATE_LIMITED`, RFC 9457 like every other error, `Retry-After` in whole seconds rounded up, and the header triple with zero remaining; the detail is `states.md` §1b's copy — *"Please wait 3 minutes before trying again."* — the wait and nothing else, not the bucket, not the count, not the word "attempts". On a **successful** response the headers describe the bucket the interceptor consumed with the fewest tokens left; a 401 from the service still carries them. On a 429 raised by a service bucket, the headers describe that bucket. `X-RateLimit-Reset` is Unix seconds (GitHub's convention) at which the bucket is full again, which after a single consume is one refill interval away, not the whole period. The interceptor throws rather than writing the response, so the 429 goes through the same `@RestControllerAdvice` chain as everything else and the headers are set once, in `SecurityExceptionHandler`.

**5. Fail-open, loudly.** If Redis does not answer, the answer is *allow*, and the request proceeds without headers. Doc 07 §5's rule decides it: Redis is a coordinator, never a source of truth, and a cache outage must not become an authentication outage. What still stands when the limiter is gone: Argon2id's per-attempt cost, the silent exponential lockout in Postgres (ADR-0020), and the unique constraints. "Loudly" is three things: a WARN at most once per five seconds rather than once per request; the counter `moyi.rate_limit.backend_unavailable`, which is what an alert watches; and a five-second hold after a failure during which Redis is not tried at all, so an outage costs one timeout per interval rather than one per login. When the hold expires, a compare-and-set gate lets **one** caller probe while every other request keeps failing open, and only the caller that moves the hold forward writes the WARN — without that gate every request that saw the expired hold probed together, which Codex's review of #33 caught: N timeouts per interval under load, not one. The timeouts are short on purpose — 500 ms to connect, 250 ms per command — because Lettuce's default is sixty seconds, which is a login outage by another route. **The Redis health indicator is disabled**: kamal-proxy routes on `/actuator/health`, and reporting DOWN for a cache would take the application out of rotation to protect the thing it can live without. The application boots with Redis absent; the first consume connects. `moyi.security.rate-limit.enabled=false` replaces the limiter with one that allows everything and says so at WARN on every start — a test context's lever and an operator's, not a deployment option.

**6. The client address: walk `X-Forwarded-For` from the right, past the proxies we trust.** `moyi.security.client-address.trusted-proxies` is a list of CIDR ranges. The socket address, if trusted, is skipped; then the header's entries from right to left, skipping each trusted one; the first untrusted entry is the client. Anything to its left was written by somebody we do not trust and is ignored, which is what makes a forged header worthless. **An empty list means no header is believed** and the socket is the client — over-strict behind a proxy (every request shares one address, and the per-IP limits say so at once) rather than spoofable, and correct on a laptop. Header entries are parsed as literals and never resolved: `InetAddress.getByName` on an attacker's string is a DNS lookup on the request thread. An entry that does not parse ends the walk. **IPv6 is keyed on its /64**: an ordinary allocation is at least that, and a per-/128 bucket hands one connection 2^64 fresh keys. `consent_records` stores the hash of the full address; the key truncation is the limiter's alone. The `local` profile trusts loopback so that a request from the developer's own machine may name its client with the header, which is how `scripts/smoke.sh` gives each probe an address and drives every per-IP bucket to its 429 against the real jar.

**7. Personal identifiers are hashed with a keyed hash and a configured secret.** `PersonalDataHasher` is HMAC-SHA256 over `moyi.security.hashing.secret`, base64url, forty-three characters. Plain SHA-256 of an IPv4 address is reversible by hashing all 2^32 of them, which takes minutes; the secret is the only thing that turns "we store hashes" from a courtesy into a control. The same hasher keys every Redis bucket, so no address or email is a Redis key in the clear (NFR-044). The secret **fails closed** like the signing key (ADR-0019): `secret-source` defaults to `CONFIGURED`, which refuses to start without at least thirty-two characters from the environment; `EPHEMERAL` is set only by the `local` profile and test contexts, and logs at WARN. Registration now fills `ip_hash` and `user_agent_hash`, which closes the note doc 07 §2 has carried since slice B; V3's own column comment still says "NOT populated yet" because a Flyway migration is immutable once applied, and this ADR is where the correction lives.

**8. The rate limit and the lockout are two layers, and the rate limit fires first.** With five per fifteen minutes per email and a lock after five failures (ADR-0020), the sixth attempt inside the window is a 429 and the lock is never observed over HTTP until a token refills. That is the intended order: the bucket is the cheap front door — no Argon2id, no database write — and the lockout is the durable one that survives a Redis outage and counts across addresses. The endpoint tests turn the limiter off for the shared context, because the lockout tests sign in six times in a row, and one dedicated context turns it on and proves every bucket; the smoke script flushes the compose Valkey between sections for the same reason.

## Consequences

**Positive.** Every bucket in doc 06 §4 that has an endpoint is enforced, each 429 carries `Retry-After`, and the headers are on every limited response (doc 12 §3.3). A login brute-force writes to Redis and never to Postgres. A Redis outage costs limits, not logins, and is visible on a counter. A forged `X-Forwarded-For` buys nothing; a misconfigured proxy list under-trusts rather than over-trusts. The consent rows carry evidence that cannot be turned back into an address. No bucket maths, no Lua and no address parsing beyond a shape check is hand-written.

**Negative.** A 422 spends a per-IP token. A person who signs in on six devices inside fifteen minutes waits three minutes. Two more required environment values before anything but `local` boots (`MOYI_SECURITY_HASHING_SECRET`, and the proxy ranges in production). `common:security` now carries Spring Data Redis and Bucket4j, and so does `tools:breach-corpus`, which depends on it for the Bloom filter and calls none of this; ADR-0019 already named that smell. The `local` profile trusting loopback means a process on the same machine can claim any address — acceptable for a laptop and wrong anywhere else, which is why it is profile-scoped. Bucket4j's Lettuce adapter is one major version behind the Lettuce we run; the integration tests are the guard, and a Lettuce 8 that changes `eval` would fail them, not production.

**Neutral.** The `X-RateLimit-*` names are doc 06's; the IETF draft (`RateLimit`, `RateLimit-Policy`) may be adopted later as an addition. The kill switch exists and is documented as not a deployment option; the WARN on every start is what keeps it honest. Doc 07 §5's fifteen-minute cache of `tokens_invalid_before` is still not built; the Redis slice this ADR belongs to could carry it, and it must sit behind the `TokenRevocations` port with Postgres as the fallback (ADR-0019), which is a separate change.

## Alternatives considered

- **Chirp's hand-written Lua bucket over `StringRedisTemplate`.** Rejected by D6 (Bucket4j is named) and by D5's spirit: the compare-and-swap and refill arithmetic are exactly the code that is wrong in a subtle way first. Good to read for atomicity; not to ship.
- **Bucket4j's JDBC backend on Postgres.** Rejected for now by D6's own argument — every unauthenticated request writes — and kept as the fallback D6 names if Redis is cut for memory: a one-session change behind the `RateLimiter` port.
- **Fail closed.** Rejected: it converts a cache outage into an authentication outage, and the controls that remain are adequate. Revisit if a credential-stuffing run is ever observed coinciding with a Redis outage.
- **Tomcat's `RemoteIpValve`** (`server.forward-headers-strategy=native`). It does this job, rewrites `remoteAddr` for everyone, and is the answer in a Tomcat-only shop. Rejected because its trusted list is a regular expression, which for Cloudflare's published ranges is unreadable, and because a class the tests can hold with a CIDR list is smaller than the valve's configuration. Spring's `ForwardedHeaderFilter` trusts every hop and was never a candidate.
- **`CF-Connecting-IP`.** Cloudflare's own header names the client directly; trusting it means trusting that only Cloudflare can reach the origin. Not built; the CIDR list can express "trust Cloudflare's ranges" when the deployment is real, and the header can be added then if the walk proves fragile.
- **Plain SHA-256 for `ip_hash`.** Rejected; see decision 7. A pepper in code rather than configuration was rejected for the same reason a signing key in the repository was.
- **Refund the login token on success.** Considered so that a person signing in repeatedly is never limited; rejected as one more branch on the success path for a case (six sign-ins in fifteen minutes) that a single account does not have.
- **Per-/128 IPv6 keys.** Rejected; see decision 6.

## Revisit when

Redis is cut during Phase 5 load testing (move to Bucket4j's JDBC backend behind the same port). A second application node exists (the buckets are already shared; the hold and WARN are per process). The deployment is real and Cloudflare's ranges have to be configured (and refreshed — they change). The invite buckets of doc 06 §4 arrive with Phase 2 (`invite:lookup` + `invite:accept` share one per-IP bucket, which needs a bucket that two annotations can name). A 429 is ever seen on a legitimate client's ordinary use of `/me` polling (raise the global bucket, or shape the client). Lettuce 8.
