# ADR-0021 — Refresh rotation, reuse detection, and what a family revocation tells the person

**Status:** Accepted · **Date:** 2026-09-23 · **Amended:** 2026-11-08 (a 30-second grace window for a lost refresh answer; decision 3 superseded, issue #136)

## Context

Doc 09 §3 specifies the refresh token in five lines: 256 bits of CSPRNG output, stored hashed, thirty days, rotated on every use, and "presenting an already-rotated token means it was stolen (either by the attacker or the victim). The entire token *family* is revoked immediately, and the user is emailed." Doc 06 §3.1 gives the endpoint and the code: `POST /auth/refresh` returns a new pair; reuse returns `401 TOKEN_REUSE_DETECTED`. Doc 13 tells the client what to do on that code: wipe local credentials, clear the cache, route to sign-in with an explanation. Doc 25 D5 calls this "the mechanism that makes stateless auth safe, and the single most probed backend topic in interviews."

The first implementation had the rotation and the family revocation and missed the two halves that face outward: every refresh failure was `UNAUTHENTICATED`, so the client could not tell a stolen session from an expired one, and nobody was emailed. It also revoked the family of any account whose status was not `ACTIVE`, which signed unverified users out on their first refresh.

## Decision

**1. Rotation is a conditional `UPDATE`, and the successor is inserted in the same transaction.** `UPDATE refresh_tokens SET rotated_at = :now, replaced_by = :successor WHERE id = :id AND rotated_at IS NULL AND revoked_at IS NULL AND expires_at > :now`. Row count `1` means this request rotated it; `0` means somebody else did a moment ago. The same compare-and-set shape as verification consumption (ADR-0018) and for the same reason: two concurrent presentations must have exactly one winner, and only the database can arbitrate.

**1a. Every mutation of a user's sessions first takes a per-user advisory lock.** `pg_advisory_xact_lock(1, hashtext(user_id))`, transaction-scoped, taken by rotation, `logout`, `logout-all`, password reset and login's family issue, before the state they act on is read. The compare-and-set in (1) is necessary and not sufficient: a family revocation is a single `UPDATE` over the rows in its snapshot under READ COMMITTED, and a rotation committing concurrently can insert a successor that snapshot never saw — a "revoked" family with one live token in it, held by whoever was refreshing, which after a reuse may be the thief. The Codex review of the first version found this; a two-transaction test now reproduces it and fails when the lock is removed. Per user rather than per family so there is one lock and no ordering to get wrong; a user has a handful of concurrent sessions, so the contention is nil.

**2. Three outcomes, three codes.** A token whose `rotated_at` is set — or whose `UPDATE` in (1) returned `0` — is a **reuse**: the family is revoked, a WARN names the user and family, the person is emailed, and the response is `401 TOKEN_REUSE_DETECTED`. A token that is unknown, expired, or in a family already revoked is **invalid**: `401 REFRESH_TOKEN_INVALID`, nothing revoked, nobody emailed — a second presentation of a stale token after the family is gone is not a second theft. A live token is **rotated**. The two 401 codes exist because the client's correct responses differ: sign in again, versus sign in again *and* explain that the session may have been stolen.

**3. Strict, with no grace window.** *(Superseded on 2026-11-08 by the amendment below: a retry inside 30 seconds, while the successor is unused, is rotated again. The rest of this paragraph is the original reasoning, kept because the amendment answers it.)* Two legitimate concurrent refreshes of one token — two tabs, a retry after a timeout — will trip reuse detection and end the family. That is the trade doc 09 makes and doc 13 pays for with a client-side mutex so the app never sends two. The alternative, a short window in which the immediate successor is accepted from the same family, weakens the guarantee exactly where it matters (a thief who acts within the window is indistinguishable from a retry) and is recorded here so nobody re-derives it as an improvement.

**4. The email goes out after the commit, through the same listener shape as verification.** A `SecurityNotice.SessionReuseDetected` event is published inside the revoking transaction and delivered by an `AFTER_COMMIT` `@Async` listener to `notification`'s `EmailSender` (ADR-0017), keyed by family id so a retry cannot send twice. The message is written for both readers doc 09 names: the victim, who needs to know to change their password, and the person holding the stale copy, who needs to know why they were signed out. **It is honest about scope**: that sign-in ended; other devices and outstanding access tokens did not (the first draft said "every device has been signed out", which was false and would have let a victim believe the account was secured). Changing the password is what signs everything out, and the email says so. The password-changed notice is keyed by user *and* change time, so a second reset is a second email and not a "retry" the provider swallows. Under ADR-0008 this is a non-critical event: the *protection* is the revocation, which has already committed; the notice is the part a process death could lose.

**5. FR-002 applies to refresh as it does to login.** An account that can sign in (`ACTIVE`, `PENDING_VERIFICATION`) can refresh. One that no longer can has its family revoked on the next refresh — as invalid, not as a reuse, because nobody did anything wrong with the token.

**6. `logout` revokes the presented token's family and is idempotent; `logout-all` revokes every family and bumps `tokens_invalid_before`.** `logout` needs no bearer token — the refresh token is the credential — and returns `204` whether or not the token existed, so it cannot be used to test tokens. `logout-all` needs a bearer token and, through ADR-0019's revocation validator, kills outstanding access tokens too.

## Consequences

**Positive.** A stolen refresh token is worth at most one rotation before the theft is detected, and detection is total: the thief's chain and the victim's are one family, and the lock means "revoked" means revoked. The person finds out. The client can distinguish the case that needs an explanation from the one that does not.

**Negative.** Legitimate concurrent refreshes end sessions; the client mutex is load-bearing. The advisory lock serialises a user's session mutations, so a user's own devices refreshing at the same instant queue behind each other for a few milliseconds. Every family revocation on reuse sends an email, which is also an abuse surface — someone holding a stolen token can make the victim receive one email per family they compromise, which is the least of that victim's problems. The `iat` one-second resolution from ADR-0019 means an access token issued in the same second as `logout-all` survives it.

**Neutral.** `used_at` from doc 07 is not populated: `rotated_at` is the moment a token is used, and one column saying so is enough. `replaced_by` is populated and is what makes a family readable as a chain.

## Alternatives considered

- **One `UNAUTHENTICATED` for every refresh failure** (the first implementation). Rejected: doc 06 names `TOKEN_REUSE_DETECTED`, and doc 13's client behaviour depends on it.
- **No email on reuse.** Rejected: doc 09 requires it, and it is the only way the victim learns.
- **A reuse grace window.** Rejected in (3); adopted, in a narrower form, by the 2026-11-08 amendment.
- **Delete-and-reissue instead of mark-rotated** (Chirp's model). Rejected: a deleted token cannot be recognised as *reused*, so reuse detection is impossible — the stale token is simply "not found", the same answer as garbage.
- **Refresh tokens as JWTs** (Chirp). Rejected: an opaque secret stored as a hash can be revoked; a signed token cannot be un-signed.

## Revisit when

The client team reports legitimate reuse trips in the field (measure before adding a window). Doc 07 §5's Redis denylist for single-session access-token revocation is wanted (it would make `logout` kill the access token too). FR-007's session list lands (`revoked_reason`, currently unused, is where "revoked by user from settings" goes).

## Amendment — 2026-11-08: a 30-second grace window for a refresh whose answer was lost

**Context.** Issue #136, filed from the mobile client. The mutex doc 13 asked for stops a client sending two refreshes at once; it cannot stop the one case the client cannot see. When the *answer* to a refresh is lost after the request reached the server — a read timeout, a reset connection, the app killed mid-flight — the server has rotated R1 to R2 and the client still holds R1. Its next refresh presents R1, and under (3) that ended the session and emailed the person that their sign-in may have been stolen. On the connections Moyi is built for, that is not rare, and it teaches people to ignore the one email that matters. The "revisit when" below asked for field reports before adding a window; the client now logs these under `SessionRefreshAmbiguous`, and the owner ruled on 2026-11-08 without waiting for the rate: a 30-second grace window. The issue's other option, an `Idempotency-Key` that replays the same R2, was not taken: replaying a response means storing the plaintext refresh secret (or a way back to it) for the window, which this table was designed never to hold.

**Decision.**

**3′. A rotated token presented again is rotated again — a new pair, no revocation, no email — when all of these hold**, and is a reuse under (2) otherwise:

- it was rotated by being used, not *voided* (below);
- its direct successor (`replaced_by`) exists and has not been used: not rotated, not voided, not revoked, not expired;
- no more than `moyi.identity.refresh.grace-window` (default **30 s**, `RefreshProperties`, the one place the number is written; `0` restores strict rotation; more than two minutes is refused at start-up as a typo) has passed since the token's `rotated_at`.

The retry voids the unused successor — `voided_at` and `rotated_at` set to the same instant, V50 — mints a new one, and points the presented token's `replaced_by` at it. The response is the ordinary `200` token pair; no new error code exists and the client changes nothing. The rule is `RefreshToken.admitsRetry`.

- **The window runs from the first rotation, and a retry does not move it.** `rotated_at` is not touched by a retry, so a client that keeps losing answers gets 30 seconds in all, and a thief cannot keep it open.
- **It is measured from `rotated_at`, which is the rotating request's clock reading, not its commit.** Rotation reads the injected `Clock` once, inside its transaction and after it holds the sessions lock; the commit follows within milliseconds. The effective window after the client could first have received R2 is that much shorter than 30 s, which errs on the strict side. The read is after the lock on purpose: read before it, as the first version of this amendment did, a request that waited on a concurrent rotation acted at an instant *before* that rotation, and with the window at 0 it was let through as a grace retry instead of a reuse (security review of #153). `admitsRetry` also refuses everything when the window is 0, so the kill switch does not depend on two requests' clocks. Both instants are truncated to microseconds before they are stored or compared, because Postgres rounds `timestamptz` and the comparison is against what comes back.
- **A voided token is never itself eligible.** It has no successor of its own (a `CHECK` in V50 holds `voided_at` to "rotated at that instant, replaced by nothing"), and `admitsRetry` refuses it explicitly. Without that, two holders of one family could void each other's tokens in turn for as long as each stayed inside the window, and nobody would ever be told.
- **Concurrency.** Two presentations of R1 at once — a client retry racing itself — must not leave two live tokens. Rotation already takes the per-user sessions lock (1a); it now also reads the presented token and its successor with `SELECT … FOR UPDATE` after that lock, and the lookup by hash returns a projection rather than an entity, so the read after the lock is a real read and not the persistence context's copy from before the wait. (Before this, a refresh that waited on a concurrent revocation read the token as still live, lost the compare-and-set, and called it a reuse: an email for a theft that never happened. The row-lock test reproduces that and fails without the lock.) The two presentations therefore run one after the other: the first rotates, the second is a grace retry that voids the first's successor. Both get a `200`; exactly one token is live. The void and the re-point are compare-and-sets too, and fall back to a reuse if what they expect has gone.

**The adversarial analysis.** The window is time in which a stale token is honoured, so it is exactly where a thief gains. The question is what the thief gains and whether the theft is still detected.

1. *The thief replays R1 inside the window, before the client has used R2.* The thief gets R3 and a 15-minute access token; R2 is voided. The legitimate client, still holding R2, presents it at its next refresh (within about 15 minutes, when its access token expires). R2 is voided, so that is a **reuse**: the family is revoked — R3, and anything the thief rotated it to, with it — the WARN is written and the person is emailed. The theft is detected one step later than under strict rotation, not missed. The thief keeps the access token minted for R3 until it expires, as any thief who rotated first always has (ADR-0019; the "Negative" consequences above).
2. *The thief replays R1 after the client has used R2.* R2 is used, so R1 is a reuse whatever the time: revoked and emailed at once, as before.
3. *The thief replays R1 after 30 seconds.* A reuse, as before.
4. *The client loses the answer and retries R1; nobody else holds it.* The case the window exists for: a new pair, no email, R2 (which nobody received) voided.
5. *The client and the thief alternate inside the window.* Through the successors, impossible: a voided token is not eligible, so the first holder to present a voided token ends the family. **Through R1, possible:** both hold R1, and each retry of R1 inside the window voids the other's unused successor and gets a pair, so the two can take turns for up to 30 seconds without an alarm. Detection is delayed, not lost: once the window has passed, R1 is a reuse, and the holder of the most recently voided successor presents a voided token at its next refresh. Either way the family is revoked and the person is emailed. (Found by the security review of #153.)

What changed for the attacker, then, is case 1: a stale token stolen within 30 seconds of its rotation now behaves like a **live** token stolen outright — usable once, detected when the victim next refreshes. Strict rotation detected it on the thief's first use. That is the cost, and it is bounded by the window: a thief needs a copy of a token that was valid seconds ago, which in practice means the same position (a compromised device or a TLS interception) from which the live token could have been taken anyway. Where the victim never refreshes again — the app uninstalled — the thief's family lives until it is revoked or its tokens expire, which is also true of a live token stolen today.

**Consequences.** The false `TOKEN_REUSE_DETECTED` of issue #136 is gone for retries inside 30 seconds; a retry after that still ends the session, which is the client's ambiguous-failure path to keep measuring. A legitimate concurrent refresh (two tabs) inside the window no longer ends the session either, though the client mutex is still wanted: the second request's pair replaces the first's, and a client that kept the first one's refresh token would present a voided token next — a reuse. The sessions list is unaffected: a voided token is not live, so it is in no list and no count. The tests are `RefreshGraceWindowTest` (the window's edge to the microsecond, the voided successor caught, the used successor, the window not extended, the account that can no longer sign in, the two simultaneous retries synchronised on the sessions lock through `pg_blocking_pids`, the row lock) and `RefreshTokenTest` (each condition of the rule alone).

**Revisit when** the client's `SessionRefreshAmbiguous` measurements show retries arriving after 30 seconds (the window is a property, but a longer one is a new decision about case 1, not a configuration change), or when access tokens become revocable per session (doc 07 §5's denylist): then the voided pair's access token could die with it and case 1 would cost the thief more.
